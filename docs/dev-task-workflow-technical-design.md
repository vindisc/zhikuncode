# SkyCode「开发任务」工作流首期技术方案

- **状态**：设计基线，供交叉评审与后续实现拆解；尚未实现。
- **日期**：2026-11-28
- **范围**：SkyCode Web 工作台、后端开发任务域、现有 Agent 执行引擎适配。
- **命名约定**：代码域采用 `devtask` / `DevTask`，API 前缀 `/api/dev-tasks`，数据库表前缀 `dev_tasks_`；界面统一称“开发任务”。本文中的“工作流”描述流程机制，不作为新模块类型名。

> 本方案基于产品讨论和多轮只读代码勘察整理。已确认决策与建议默认值分开标识，避免把建议误当成已批准的产品决策。没有代码、测试或性能验证结论。

## 1. 目标与原则

为一次需求或缺陷提供一个持久、可审查的开发任务空间，将需求分析、技术方案、编码、测试方案和测试执行串成阶段化流程。每阶段可由 Agent 执行并产出持久资料；人工可以确认、跳过、阻塞或重试。任务时间线记录用户输入、阶段变化、执行结果、审批和证据。

设计原则：

1. **任务是业务聚合根**：一次任务不等于一个聊天会话，也不等于一次 Agent Run。
2. **新旧模式隔离**：保留现有聊天与工作台；新增模式入口和面板，不导入旧会话、不跨模式接续同一任务。
3. **流程与执行分离**：任务/阶段状态由开发任务域管理；每次阶段执行调用现有 QueryEngine/Run 能力，但使用内部执行会话。
4. **结论持久化**：Run 上下文是短暂执行状态，任务阶段资料、审批、事件和重试摘要必须有自己的持久记录。
5. **人做最终裁决**：Agent 给出证据、归因和建议；测试例外是否接受及任务完成由人确认。
6. **诚实描述安全边界**：首期沿用现有工具权限机制，不声称工作区是沙箱，也不扩大为严格目录隔离。

## 2. 已确认的产品决策

- 一个开发任务代表一次开发工作（需求或缺陷）。
- 首期只允许在新“开发任务”模式创建任务；不提供从旧会话导入或转换。
- 旧模式和开发任务模式保留各自数据与工作方式。切换入口仅用于选择面板，不允许同一任务跨模式继续。
- 两种创建路径：
  - 从当前工作区/代码仓库创建，自动关联该目录；
  - 从开发任务中心先建任务，关联工作区后才能开始需求分析。
- 工作区是目录，可包含多个 Git 仓库，不限制为单仓库。
- 流程模板固定，但阶段允许按需跳过。
- 技术方案、测试方案等阶段的人工确认策略需要可配置。阶段确认是任务域持久审批，不是 Agent 运行时工具授权。
- 测试平台、CI/CD、发布部署不属于首期范围。
- 测试通过是正常完成依据，但不能仅以通过率机械判断：遗留问题或非本次改动导致的失败可以例外处理；例外必须有证据、归因和处置，并由人确认。
- Agent 负责整理测试结果与完成建议，不独自裁定例外或最终完成。

## 3. 建议默认值（需产品负责人确认）

以下是面向实现的推荐值，不与上节已确认决策混为一谈：

1. **阶段执行权限**：任务级权限模式默认 `DEFAULT`；`AUTO_APPROVE` 只能由用户主动选择，并在 UI 明确说明风险。
2. **值守语义**：`DEFAULT` 下阶段执行可能需要人工处理文件或工具授权。按当前交互实现，首次等待传输最长 600 秒、ACK 窗口 5 秒、ACK 后决定窗口 300 秒；超时可能终止当前 Run。阶段因此进入“受阻”，数据保留，可重试；首期不改共享交互时限。
3. **默认工作区登记**：关联工作区时，如路径正是配置的默认根且尚未登记，尝试自动登记为 Project。UI 必须说明“登记后，项目内文件写入可能按 DEFAULT 自动放行”。策略拒绝登记时仍允许关联，但警告每次写入可能请求授权。
4. **跨 Run 修复轮数**：设置任务级/系统级可配置上限；建议首期默认最多 3 轮“测试失败后修复并重新验证”。超限进入待人工确认，不自动完成。最终值可由实现前评审调整。
5. **用户发言**：阶段执行期间不支持插话；没有活动 Run 时允许添加任务输入，作为后续阶段 Run 的输入，并进入统一时间线。
6. **跳过阶段**：用户可跳过；要求填写或选择跳过理由，形成审计事件。若产品希望零摩擦，可将理由设为可选，但必须记录操作者和时间。

## 4. 流程模型与状态语义

### 4.1 首期阶段模板

建议固定顺序如下，阶段可以跳过；不适用阶段也应留下跳过记录：

1. **需求分析**：理解用户提交的需求/缺陷，读取工作区，生成需求摘要、影响范围、疑问和工作区地图。
2. **技术方案**：针对需要设计的任务形成实现方案、风险、文件/模块影响和验证策略；小改动可跳过。
3. **编码实现**：按已确认需求/方案修改代码，形成变更摘要和候选 diff 信息。
4. **测试方案**：根据需求和变更形成测试点、覆盖范围、环境及命令；可配置人工确认，也可跳过。
5. **测试执行**：按测试方案执行可用测试/验证命令，记录命令、工作目录、运行环境、退出码和结果证据。首期不接公司测试平台。
6. **人工验收/完成**：汇总通过项、失败项、未覆盖项、与本次改动无关的判断及遗留问题，由人确认完成或要求继续处理。

“发布/部署”明确不进入首期阶段模板。测试平台集成、CI/CD 后续以适配器或阶段能力扩展，不改变任务聚合根。

### 4.2 状态机

任务状态建议：`draft`（未关联/未开工）、`ready`、`in_progress`、`waiting_approval`、`blocked`、`completed`、`cancelled`。

阶段状态建议：`pending`、`running`、`waiting_approval`、`blocked`、`passed`、`failed`、`skipped`。

主要转移：

- 任务创建 → `draft`；工作区完成关联并通过基础校验 → `ready`。
- 阶段开始 → `running`，创建一次全新的执行 Run。
- 阶段 Run 成功 → 按策略进入 `waiting_approval` 或 `passed`；审批通过后继续下一阶段。
- 阶段执行超时、被中断、权限交互超时或基础设施错误 → `blocked`，保留错误、Run 状态、工作区快照和进度摘要。
- `blocked` 阶段可由用户发起新 Run 重试；不尝试从进程内存续跑旧 Run。
- 用户跳过 → `skipped` 并记录理由；后续阶段按模板继续。
- 测试执行失败 → 在修复轮数未超限时可发起编码修复与再次测试；超限、归因不明或建议判定与本次改动无关时转人工确认。
- 所有必需阶段完成或跳过，且例外已处置并获人工确认后，任务才能进入 `completed`。
- 任何状态写入必须支持并发幂等（版本号/CAS 或事务校验），重复审批、重复启动请求不得产生双 Run 或重复推进。

### 4.3 测试—修复循环的退出条件

每轮测试/修复均是单独 Run，因此跨 Run 上限必须由开发任务域计数，不能依赖单 Run token/轮次上限。

- 测试全部通过：提交结果证据，进入阶段审批或人工验收。
- 有失败且未超过最大修复轮次：Agent 提出修复计划，用户发言如需补充只能在无活动 Run 时提交；随后新 Run 执行修复和验证。
- 超过轮数：进入 `waiting_approval`，列出失败、已尝试修复和剩余风险。
- Agent 判断失败与本次变更无关：只能作为“归因建议”，附证据交人工判断，不得自动豁免。
- 无法归因或测试环境异常：标记阻塞/待人工，不算通过。
- 遗留问题若不在本次范围：必须记录影响、归因、处置（接受/另建缺陷/延期等）及确认人。

## 5. 总体架构

```text
开发任务工作台（新模式）
  ├─ 任务中心 / 任务详情 / 统一时间线 / 阶段产物与审批
  ├─ 开发任务 REST API（/api/dev-tasks）
  └─ 单一 STOMP 连接上的任务订阅
         │
开发任务应用服务（DevTask）
  ├─ Task / Stage / Approval / Timeline / Artifact / RetryPolicy
  ├─ 工作区绑定与多仓地图
  ├─ 执行适配器：隐藏会话 + RunControlService + QueryEngine
  └─ 事件投影、重试摘要、启动对账
         │
现有 Session / Run / QueryEngine / Tool Authorization
```

业务表放在项目级 `data.db`，与 Session/Run 使用同一项目库以便事务关联。`projects` 位于全局库，跨库没有外键；开发任务保存工作区规范化路径快照和可选 `project_id` 作为引用，不依赖跨库 FK。任务在全局项目撤销/删除后仍按快照重新校验路径存在性和策略，不能假设旧会话会随 Project 删除。

Coordinator 的 `WorkflowPhase` 等属于既有协调器领域，不复用其命名或状态语义。新类型使用 `DevTask*` / `devtask_*`，API 使用 `/api/dev-tasks`。

## 6. 数据模型建议

所有 ID 使用随机不可枚举标识；时间统一存 ISO-8601 UTC；关键实体采用 `version` 字段做乐观并发控制。

| 表 | 用途 / 关键字段 |
|---|---|
| `dev_tasks` | 聚合根：`id`、`title`、`kind`（需求/缺陷）、`status`、`workspace_root`（规范化容器路径快照）、`project_id`（可空，仅引用）、`permission_mode`、`current_stage`、`version`、创建/更新时间、完成/取消时间 |
| `dev_task_stages` | 阶段实例：`id`、`task_id`、`stage_key`、`status`、`required`、`approval_policy`、`attempt_count`、`max_attempts`、`latest_run_ref`（仅后端内部，API 不返回）、`version`、时间戳 |
| `dev_task_approvals` | 持久审批：`id`、`task_id`、`stage_id`、`approval_type`、`status`、`payload_json`/产物版本、`decided_by`、`decision`、理由、`version`、时间戳；唯一约束防同一产物重复审批 |
| `dev_task_events` | 持久时间线：`id`、`task_id`、单调 `seq`、`event_type`、`actor_type`、`actor_id`、`payload_json`、时间戳；`(task_id, seq)` 唯一 |
| `dev_task_artifacts` | 阶段资料与证据：`id`、`task_id`、`stage_id`、`artifact_type`、标题、内容/存储引用、版本、来源 Run 内部引用、创建时间；API 返回任务级 artifact ID，不暴露 Run ID |
| `dev_task_workspace_repos` | 可选的工作区地图快照：仓库相对路径、识别结果、HEAD、构建/测试命令、来源和确认状态；可先将地图 JSON 作为版本化 Artifact，确认后再规范化为表 |
| `dev_task_run_links` | 内部关联：任务/阶段/尝试到隐藏 session 和 Run 的映射；只供后端内部查找与清理，禁止 API 序列化 |

阶段审批、时间线和产物不可只存在于 Run 事件日志：Run 日志存在保留期限，且旧 Run 事件可能定时清理。任务时间线与关键证据按任务生命周期保留。

任务删除必须在事务/可靠清理流程中显式清理隐藏 Session、Run envelopes、Run events 和任务域表。删除 Session 会级联清理部分 Session 子表，但 `run_envelopes` 对 Session 没有外键，不能假设其自动级联。首期可优先提供归档/软删除；若实现硬删除，必须覆盖全部关联表并提供失败重试与审计。

## 7. 隐藏执行会话与旧模式隔离

现有 Run 根记录需要真实 `sessions` 行，授权主体也从根 Run 的会话读取工作目录；多个相关表对 Session 有外键。执行适配器应采用现有“注册隐藏会话 → 创建 Run → `QueryEngine.execute`”模式。

- 使用不会变更进程级当前会话的记录/注册 API（如 `createSessionRecord` 或适配的内部注册方法）；不得用会触发全局当前会话切换的 `createSession` / `resumeSession`。
- 每个阶段执行/并发执行单独使用 session ID。阶段 Run 结束即结束执行会话；阶段批准不占用运行中的 Interaction。
- 不将隐藏 Session ID、Run ID 发给浏览器。前端使用 `taskId`、`stageId`、`artifactId` 操作任务。
- 在集中会话加载入口增加外部访问拒绝；执行适配器通过受限的内部方法访问隐藏会话。该守卫不能挡住现有子 Agent 对父会话的读取；现有前端没有按内部 ID 直达子 Agent/fork 会话的产品路径。
- 会话列表的子 Agent 过滤改为基于明确 `session_kind` 字段的共享谓词，迁移时回填既有 subagent 数据，避免散落字符串 `LIKE` 判断。Session 类型字段须有安全默认值，迁移可回滚且不改变历史会话可见性。
- `RunController` 用户列表本身按会话过滤；详情/事件通过 `accessibleRun` 校验 Session。隐藏会话拒绝守卫是隔离基础，Run ID 不出 API 是第二道防线。
- 在执行适配器与 Session 守卫落地前，先写特征测试：现有子 Agent 正常运行；外部用户不能按隐藏 Session ID 查看/更改/删除/续聊；隐藏 Run 不能从旧 API 读取、取消或取事件。

## 8. 权限交互和阶段审批

两类交互必须严格区分：

1. **阶段审批**：例如确认技术方案、测试方案、例外处置。使用 `dev_task_approvals` 持久化；Run 已结束后可等待数小时/数日，不占用 Agent 进程，不受 Interaction 600/300 秒时限控制。提交带审批 ID、版本/幂等键，重复决定返回现态或冲突，不重复推进。
2. **执行时工具授权**：Agent 正在读写文件、执行命令等产生的运行时权限请求。继续使用现有 Authorization/Interaction 业务，但任务工作台需要能够承接隐藏会话授权。

前端不能创建第二个 STOMP 客户端：当前 `createStompClient()` 会停用既有模块单例连接，第二个客户端会与聊天互相断连。采用同一 STOMP 连接上的额外任务队列订阅（沿用 `useStompSubscription` 的生命周期/重连恢复模式），服务端维护连接到任务的订阅关系，并鉴权用户对任务的访问。

服务端通过任务订阅者投递待授权通知；任务 UI 有专用 ACK 和授权决定端点，或在现有 ACK/决定处理器中添加受鉴权的任务订阅者回退路径。不得仅凭任务订阅关系跳过交互所属 Session/Run 的授权校验。无订阅连接时持久化请求并允许重新投递；按现有交互期限到期的结果应投影为阶段 `blocked`，附可重试原因。

权限建议：任务级默认 `DEFAULT`；只有用户明确选择才用 `AUTO_APPROVE`。工作区级“记住授权”按现有目录/工作区授权主体可能被同一目录下旧模式共享；会话级授权在每次新建隐藏会话时不能自然复用。UI 和方案都应说明作用域，避免误以为是任务私有授权。

**安全限制**：当前 Bash 无工作区目录约束；部分越界文件访问走权限判断而非必定拒绝。首期沿用现状，不宣称开发任务具备强沙箱或目录隔离；默认 `DEFAULT`、受信任 Project 自动放行和 `AUTO_APPROVE` 的风险必须清晰展示。

## 9. 工作区与多仓语义

- 工作区根目录是任务执行的 `cwd`；每次执行前规范化/解析真实路径，并验证仍存在、可读写且符合当前允许根策略。
- 根目录可能不是 Git 仓库。首期不实现多仓 Git 抽象，也不保证 `/git`、`/diff`、`/review`、`/commit` 等依赖根目录 Git 的命令在多仓目录可用；各仓 Git 操作通过 Bash 在对应子目录执行。
- 需求分析阶段生成“工作区地图”：根目录下识别出的仓库路径、各自 HEAD、语言/构建配置线索、建议测试命令、指令文件、未知项。模型推断内容标记为建议，用户可修订/确认；后续阶段提示词显式带入地图版本。
- 当前引擎只读取根目录 `skycode.md`，不原生识别多仓子目录指令或 `AGENTS.md`。地图应记录发现的指令文件，但不能声称引擎会自动应用它们。后续可独立扩展指令发现策略。
- 每轮重试前重新读取工作区地图和各仓 HEAD/状态；记录环境（容器/执行镜像标识、工作目录、命令、退出码）。首期不做 Git 自动回滚，只记录基线和实际变化。
- Project 是全局库授权记录，Session/Run/任务位于项目库。保存规范化路径快照；Project 被撤销或删除不自动删除任务。每次执行时重新校验路径与策略，路径不可用则阻塞并提示重新关联。
- 默认 `/app/workspace` 在当前 Compose 中位于 `SKYCODE_WORKSPACE_ALLOWED_ROOTS` 下，可以通过创建策略；自动登记时按规范路径先查已有 Project，再调用创建，并对并发重复路径冲突做二次查询。若策略/目录校验拒绝，关联可以继续但不得标成已登记/可信，提示每次写入可能请求授权。

## 10. 阶段上下文与重试恢复

上下文分层而不是无限累积对话：

- **任务持久上下文**：原始需求、确认后的验收条件、工作区根、工作区地图及版本、阶段产物、用户补充、审批决定、测试证据、遗留问题。
- **单次 Run 输入**：阶段指令、相关任务摘要、上游阶段确认产物、最新工作区地图、当前测试/修复轮次、允许工具/权限模式。
- **单次 Run 输出**：阶段结果、结构化产物、测试证据、事件流及结束状态。由应用服务从 Query/Run 事件投影到任务时间线，不能依赖旧聊天 session 消息承载完整任务历史。
- **重试输入**：除本阶段原始输入外，必须包括上一次 Run 的持久事件时间线摘要（已完成/尝试的动作、改动文件、命令和结果、未完成事项、权限/错误阻塞、建议下一步），并重新读取当前 HEAD、工作区地图和工作区状态。摘要来源需标记为自动生成且可审查；不能将摘要当作事实凌驾于当前文件状态。
- 不对 Run 上下文做自动续跑。服务重启时根据持久 Run 状态完成对账：活动 Run 被底层标记 interrupted 后，将对应阶段标记 blocked/interrupted、保存摘要和恢复说明，用户可重新开始该阶段。

## 11. 时间线、实时事件与深链接

统一时间线至少包含：用户发言、任务创建/工作区关联、阶段开始/结束/跳过、审批请求/决定、运行进度摘要、测试结果、重试、受阻/恢复和完成决定。用户发言接口只在任务无活动 Run 时接受。

- 时间线以 `dev_task_events` 数据库记录为权威，`seq` 作为游标；STOMP 只作低延迟通知，不作为唯一数据源。
- 断线后用 REST 按 `afterSeq` 补取；同一事件重复推送由事件 ID/seq 去重。阶段结束靠应用事件投影，并由启动/周期性对账补偿漏投影，不依赖某个 Bean 初始化先后。
- 新增任务 ↔ STOMP 连接订阅登记与鉴权；同一用户可订阅多个任务，连接重连后前端恢复当前任务订阅。不要重用“一个连接绑定一个真实 Session”的语义替代任务订阅。
- 前端现状没有正式路由。若首期承诺任务直达链接，应新增 URL 路由并覆盖刷新、登录回跳、面板切换、浏览器前进/后退和未授权/不存在任务；若不做，则首期从任务中心进入并明确不支持深链接。
- 旧、新面板切换仅切换工作台视图，不映射当前任务到旧会话；返回旧面板后仍是旧面板原有会话状态。

## 12. API 草案

所有请求以已认证用户为主体，并在任务维度鉴权；API 响应不含内部 Session ID、Run ID、原始权限主体或不可公开路径细节。

| 方法 | 路径 | 语义 |
|---|---|---|
| `POST` | `/api/dev-tasks` | 新建任务，可选从当前目录创建；无目录时为 draft |
| `GET` | `/api/dev-tasks` | 当前用户可见任务分页列表 |
| `GET` | `/api/dev-tasks/{taskId}` | 任务、阶段状态和摘要 |
| `PATCH` | `/api/dev-tasks/{taskId}` | 更新标题、需求、权限设置等；版本校验 |
| `PUT` | `/api/dev-tasks/{taskId}/workspace` | 关联/重新关联工作区，执行规范化、策略校验及 Project 登记流程 |
| `POST` | `/api/dev-tasks/{taskId}/start` | 开始当前阶段；幂等并发保护 |
| `POST` | `/api/dev-tasks/{taskId}/stages/{stageId}/skip` | 跳过阶段并记录理由 |
| `POST` | `/api/dev-tasks/{taskId}/stages/{stageId}/retry` | 新建 Run 重试，注入上次进度摘要 |
| `POST` | `/api/dev-tasks/{taskId}/approvals/{approvalId}/decision` | 对阶段产物/例外做持久审批，支持版本/幂等键 |
| `POST` | `/api/dev-tasks/{taskId}/messages` | 无活动 Run 时添加后续输入并写入时间线 |
| `GET` | `/api/dev-tasks/{taskId}/events?afterSeq=` | 时间线分页补取 |
| `GET` | `/api/dev-tasks/{taskId}/artifacts` | 查询任务阶段资料与证据 |
| `POST` | `/api/dev-tasks/{taskId}/subscriptions` | 登记当前 STOMP 连接订阅/取消订阅（也可通过 WS 消息协议实现） |
| `POST` | `/api/dev-tasks/{taskId}/interactions/{interactionId}/ack` | 对隐藏会话运行时授权请求 ACK，服务端鉴权任务订阅及当前授权请求 |
| `POST` | `/api/dev-tasks/{taskId}/interactions/{interactionId}/decision` | 提交运行时权限决定，遵守当前 grant scope 和 interaction 状态 |
| `DELETE` | `/api/dev-tasks/{taskId}` | 首期建议软删除/归档；硬删除必须显式清理隐藏 Session、Run、Run events 和任务关联数据 |

具体 DTO、HTTP 状态码、限流和 WS destination 在 API 设计/实现前补齐；关键命令均应支持并发控制、重放和幂等。

## 13. 前端工作台

- 保留现有旧面板原入口和行为；添加“开发任务”模式入口/切换按钮。切换不复制输入、不迁移会话、不改变旧数据。
- 新面板包含任务列表/新建、任务详情、阶段导航、统一时间线、产物查看、审批区域、运行状态与重试入口。
- 桌面和窄屏均支持任务导航与时间线；移动端长文本输入需考虑键盘遮挡、页面滚动、底部操作区和输入框可见性。
- 明确区分“开发任务”和已有 Agent 后台“任务”页签，避免同名入口混淆。
- 阶段审批与工具授权采用不同视觉类型和操作 API；明确显示授权范围、超时时间、可能的自动放行条件及 DEFAULT/AUTO_APPROVE 当前设置。
- 受阻、超时和服务重启恢复不能只显示通用失败；要展示原因、最后进度摘要和“重新执行本阶段”操作。
- 任务完成前展示测试通过/失败/未执行、例外归因和处置，用户明确确认后方完成。

## 14. 非目标与明确限制

首期不实现：旧会话导入/转换、测试平台集成、CI/CD、发布部署、自动 Git 回滚、跨 Run 自动续跑、执行中的用户插话、完整多仓 Git 产品化抽象、严格 Bash/filesystem 沙箱、由 Agent 自动豁免失败或自行批准例外。

首期不承诺：所有工具授权都可在任务视图无缝处理之前，旧会话绑定/ACK 逻辑已扩展并经验证；不承诺默认根登记失败后自动获得受信任写授权；不承诺现有 `/git`、`/diff`、`/review`、`/commit` 在非 Git 根目录工作；不将短期 Run event retention 当成任务时间线保存机制。

## 15. 验收标准

### 产品与隔离

- 能从工作区创建任务，也能从任务中心创建并关联目录；未关联目录不能开始需求分析。
- 首期无旧会话导入/转换入口；旧面板原有能力不回归；同一任务不能跨新旧模式接续。
- 子 Agent、fork、普通聊天等既有功能通过回归测试；外部用户不能按隐藏会话 ID 操作隐藏会话，也不能通过旧 Run API 读取/取消隐藏 Run。
- 开发任务 API 不返回隐藏 Session/Run ID；任务维度鉴权覆盖 REST、时间线、STOMP、审批和权限授权。

### 流程与恢复

- 阶段可以运行、跳过、等待持久审批、阻塞和重试；跳过/审批决定可审计且并发重复请求幂等。
- 阶段审批在 Run 已结束后仍有效；不占用运行时交互等待。
- 测试修复循环跨 Run 计数，达到上限或归因不明确时转人工处理，不自动完成。
- 服务重启后活动 Run 与阶段可对账至 blocked/interrupted；重新 Run 使用最新工作区状态、地图和上次进度摘要。

### 推送、持久化与权限

- 聊天与开发任务使用同一 STOMP 客户端连接；切换/重连不会互相踢线；任务事件支持 REST 断线补取和重复去重。
- 隐藏会话产生的授权请求能在任务视图被鉴权投递、ACK 和决定；超时结果可恢复且不丢阶段资料。
- `DEFAULT` 与 `AUTO_APPROVE` 的差别、信任 Project 自动放行行为和跨旧/新模式的工作区授权共享风险有明确 UI 文案。
- 默认根登记成功/已登记/策略拒绝三种情况均有正确反馈；失败关联可继续但不错误标为可信。

### 测试与交付

- 先为执行适配器、内部会话隔离、Run 隔离、权限投递/ACK、启动对账、默认根登记和阶段状态机补特征/集成测试。
- 之后补后端单测、前端状态/组件测试、API 集成测试以及手工端到端验证；具体验收设备和部署环境在实施计划中确定。

## 16. 推荐实现顺序与先行 Spike

### Spike 0：特征测试底座

为现有隐藏 Session 执行方式建立回归测试，确认普通 Session、SubAgent、Run 持久化、授权行为和进程级当前会话语义。

### Spike 1：隐藏执行会话

验证使用专用内部会话启动 QueryEngine Run，不改变当前聊天会话；同时确认并发阶段、Run 状态、工作目录授权主体、消息/事件投影和清理行为。

### Spike 2：隔离与旧 API 防护

增加 session_kind/可见性策略；验证会话按 ID、Run 详情/事件/取消、Interaction 端点和 WS 绑定无法访问内部会话；回归现有 SubAgent/fork。

### Spike 3：同连接任务订阅与授权闭环

在单一 STOMP 客户端上订阅任务用户队列，实现任务事件订阅登记和连接重连恢复；完成隐藏会话权限通知、任务维度 ACK/决定、无连接、过期及多标签场景。

### Spike 4：数据/状态/启动对账

实现任务表、阶段表、审批、时间线、内部 Run 映射、幂等状态机、启动时对账、blocked 重试、事件摘要及跨 Run 测试轮数。

### Spike 5：工作区关联与地图

实现目录规范化、Project 查重/登记、撤销后按路径重验、多仓地图、HEAD 与执行环境证据、策略拒绝提示。

### Spike 6：前端新面板与 API

实现模式入口、任务中心/详情、阶段/时间线/产物/审批/授权/失败重试，最后验证旧工作台未受影响和移动端输入体验。

推荐按 Spike 输出可运行的验收结果，再排正式 MVP 迭代。若 Spike 1、2、3 任一不成立，先修订适配边界，不要先铺完整 UI。

## 17. 风险清单

| 风险 | 应对 |
|---|---|
| 单例 STOMP 与任务订阅冲突 | 共用连接和订阅恢复机制，不新建第二客户端；任务订阅鉴权并提供 REST 补取 |
| 隐藏会话被旧接口按 ID 访问 | 集中加载守卫、内部专用加载方法、Run API 归属校验、ID 不出 API、特征测试 |
| 工具授权无法送达/ACK | 单独实现任务订阅者投递及任务维度 ACK/decision；纳入早期 Spike |
| DEFAULT 导致值守及超时 | 明示 600 秒首次传输/5 秒 ACK/300 秒决定窗口；超时阻塞可重试；任务级权限设置 |
| 默认根与 Project 自动放行 | 登记时明确告知；按路径幂等查重；策略拒绝时可关联但提示逐次授权 |
| 多仓被误认为引擎原生能力 | cwd 固定工作区根，生成并确认工作区地图；Git 通过 Bash 到子仓运行 |
| Run 事件保留期短于任务周期 | 任务事件/审批/产物单独持久化，不依赖 Run event retention |
| 重启或交互超时造成半成品 | 不续跑；重读 HEAD/工作区地图/文件状态并注入上次事件摘要 |
| 测试修复无限循环 | 任务域跨 Run 计数和上限，超限转人工 |
| 数据库双库不能跨库 FK | 任务表放项目库；保存 Project ID 引用和规范路径快照；每轮重新校验 |
| 删除留下 Run 孤儿数据 | 删除/归档流程明确清理 Run envelope 和 Run events，做删除失败重试与审计 |
| 文件/Bash 越界能力被误述为沙箱 | 首期明确沿用现状，不宣称强隔离；后续独立安全项目评估 |

## 18. 实施前需要最终确认的参数

技术方向没有阻塞实现规划的未知项，但以下产品参数应在实现任务拆分前明确：

- `DEFAULT` 默认权限与人工值守成本是否接受；如接受，是否允许在任务设置显式启用 `AUTO_APPROVE`。
- 默认根自动登记 Project 是否按建议启用；策略拒绝时是否仍允许以非可信方式关联。
- 测试失败后的默认最大修复轮数（本文建议 3）。
- 技术方案/测试方案审批策略的首期初始值及全局/任务级覆盖优先级。
- 是否首期支持任务深链接；若支持，将 URL 路由纳入验收。
- 阶段跳过理由是否必填。

以上参数不改变架构基线；在默认值未拍板前可按本文建议值实现为配置项，并保持可调整。
